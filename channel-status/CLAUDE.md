# 채널별 상품 판매상태 모니터링 대시보드

## 이 프로젝트가 다루는 것

여러 오픈마켓에 등록해 둔 제품이 채널마다 **지금 어떤 상태인지**를 한 화면에서 본다.
기준 단위는 **자체상품코드**(예: `MF-APL-G-3000G-0712`) 하나이고,
자체상품코드 하나가 여러 채널에 각각 등록되어 있으며 채널마다 상태가 다를 수 있다.

**이 프로젝트가 다루지 않는 것 — 매출, 주문 건수, 정산.**
숫자를 집계하는 도구가 아니다. 오직 "등록된 제품 리스트의 상태"만 본다.
매출 통합은 별도 프로젝트(`../sales-report/`)가 담당한다.

## 디렉터리

```
channel-status/
  CLAUDE.md      이 문서
  README.md      사용자용 안내
  index.html     대시보드 전체 (단일 파일)
  worker/        Cloudflare Workers 프록시 — 6단계에서 사용
    index.js
    wrangler.toml
  samples/       CSV 업로드 양식 예시
```

## 기술 스택

`../sales-report/` 와 같은 구성으로 간다.

- **단일 HTML 파일** — 프레임워크·번들러 없음
- **Tailwind CSS CDN**
- **Firebase Firestore** — 저장소. 지금은 같은 인터페이스의 localStorage 어댑터(로컬 모드)로 동작
- **Cloudflare Workers** — 채널 API 프록시 및 CORS 우회 (6단계)
- **GitHub Pages** 배포

## 명명 규칙

- **주석과 함수명은 한글로 쓴다.** `오늘변동목록()`, `상태매핑적용()` 처럼.
- **채널키는 ASCII 소문자**로 쓰고, 화면 표기만 한글로 둔다.
  Firestore 문서 ID·객체 키·CSV 헤더에 한글이 섞이면 인코딩 사고가 나기 쉽다.

  | 채널키 | 표기 | 플랫폼 | 계정 |
  |---|---|---|---|
  | `ss_mo` | 스스_MO | 스마트스토어 | MO |
  | `ss_gy` | 스스_GY | 스마트스토어 | GY |
  | `st11` | 11번가 | 11번가 | — |
  | `ssg` | SSG | SSG | — |
  | `auction` | 옥션 | 옥션 | — |
  | `gmarket` | 지마켓 | 지마켓 | — |
  | `kakao_mo` | 카카오_MO | 카카오 | MO |
  | `kakao_gy` | 카카오_GY | 카카오 | GY |
  | `toss_gy` | 토스_GY | 토스 | GY |
  | `ali` | 알리익스프레스 | 알리익스프레스 | — |

  같은 플랫폼이라도 계정이 다르면 별개 채널이다. 채널은 설정에서 추가·삭제한다.
- **상태값은 아래 4개 문자열만 쓴다.** 다른 값이 저장소에 들어가면 안 된다.
  `판매중` · `판매중지` · `품절` · `미등록`

## 날짜 규칙

모든 날짜는 **KST 기준**이고, "오늘"은 KST 자정에 넘어간다.
브라우저가 어느 시간대에 있든 같은 날짜가 나와야 하므로,
날짜 문자열은 반드시 `오늘KST()` / `날짜키(Date)` 를 거쳐 만든다. `toISOString().slice(0,10)` 을 직접 쓰지 않는다.

## 데이터 구조

상품 300개 · 채널 10개 · 하루 여러 번 수집을 전제로 잡았다.

```
상품/{자체상품코드}
  상품명            "유기농 사과 3kg"
  채널별상품ID      { ss_mo: "12345678", st11: "9876543", ... }   ← 없는 채널 = 미등록
  사용여부          true
  메모

채널/{채널키}
  표기 · 플랫폼 · 계정구분 · 활성여부 · 정렬순서
  상태매핑          { "판매종료": "판매중지", "SALE": "판매중", ... }  ← 채널 원문 → 내부 4상태

스냅샷/{YYYY-MM-DD}                     그날의 대표(마지막) 상태
  수집시각 · 회차수 · 입력방식
  상태              { "MF-APL-G-3000G-0712": { ss_mo: "판매중", toss_gy: "미등록", ... } }

스냅샷/{YYYY-MM-DD}/회차/{HHmmss}        하루 중 각 수집 기록
  수집시각 · 입력방식 · 상태
  (같은 초에 두 번 저장되면 뒤에 _2, _3 을 붙여 회차를 잃지 않는다)

변동/{YYYY-MM-DD}
  목록              [ { 시각, 상품코드, 채널키, 이전상태, 현재상태, 유형 } ]

예약/{자동ID}
  상품코드 · 채널목록[] · 예약일자 · 변경할상태 · 메모 · 완료여부 · 생성일

설정/{키}
  수집시각 · 보관일수 · 데모여부 등
```

### 왜 이 모양인가

- **날짜 문서 하나에 그날 전체 상태를 담는다.** 상품 300개 × 채널 10개면 한 문서가 60~80KB
  수준이라 Firestore 1MB 한도에 여유가 있고, 특정 날짜 조회가 문서 1건 읽기로 끝난다.
- **하루 여러 번 수집은 회차 서브컬렉션으로 뺐다.** 회차를 날짜 문서 안에 배열로 쌓으면
  수집 횟수에 비례해 문서가 커져 결국 한도에 부딪힌다. 서브컬렉션이면 몇 번을 돌려도 문서 크기가 그대로다.
- **변동은 저장할 때 미리 계산한다.** 화면에서 두 스냅샷을 비교하면 매번 전체를 훑어야 해서,
  수집 시점에 직전 상태와 비교해 `변동/{날짜}` 에 append 한다. 조회가 문서 1건으로 끝난다.
- **미등록은 값이 아니라 부재로 판정한다.** `상품.채널별상품ID` 에 그 채널 키가 없으면 `미등록`.
  스냅샷에 굳이 `미등록`을 채워 넣지 않아도 조회 시 채워진다.

### 보관

로컬 모드(localStorage)는 5MB 안팎이 한계라 스냅샷 70~80개면 찬다.
`설정.보관일수`(기본 90일)를 넘긴 **회차**를 먼저 정리하고, 대표 스냅샷은 남긴다.

## 상태 매핑

채널마다 상태 표기가 다르므로(같은 뜻을 "판매중지" / "판매종료" / `SUSPENSION` 으로 부른다),
저장 전에 반드시 내부 4상태로 접는다. 매핑표는 `채널/{채널키}.상태매핑` 에 두어
채널이 표기를 바꿔도 코드를 고치지 않고 설정에서 고치게 한다.

기본 매핑(코드 상수 `기본상태매핑`)은 다음을 포함한다.

| 내부 상태 | 채널 원문 예시 |
|---|---|
| `판매중` | 판매중, 정상판매, 승인완료, `SALE`, `ONSALE`, `selling` |
| `판매중지` | 판매중지, 판매종료, 판매안함, 미진열, `SUSPENSION`, `CLOSE`, `STOP` |
| `품절` | 품절, 재고없음, 일시품절, `OUTOFSTOCK`, `SOLDOUT` |
| `미등록` | (채널별상품ID 없음) |

매핑에 없는 원문이 들어오면 **임의로 추측하지 않는다.** 화면에 "미매핑" 으로 표시하고
설정에서 사용자가 직접 4상태 중 하나로 지정하게 한다. 잘못 추측한 상태는 변동 알림을 오염시킨다.

## 보안 — API 키를 어디에 두나

**채널 API 시크릿을 Firestore 나 localStorage 에 저장하지 않는다.**
이 대시보드는 GitHub Pages 위의 정적 페이지라 브라우저에 들어간 값은 곧 공개된 값이다.

- 실제 시크릿은 **Cloudflare Worker 의 Secret** 에 둔다 (`wrangler secret put`).
- 대시보드 설정 화면은 **어떤 채널에 인증이 등록됐는지 여부와 계정 식별자만** 다루고,
  키 입력란은 Worker 에 넣을 명령 스니펫을 만들어 주는 용도로만 쓴다.
- 대시보드는 Worker 엔드포인트만 호출한다. 채널 API 를 브라우저에서 직접 부르지 않는다.

## 개발 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 자체상품코드 마스터 + 채널 목록 관리 (설정) | ✅ |
| 2 | 스냅샷 구조 + CSV 수동 업로드 | ✅ |
| 3 | 채널 현황 화면 (매트릭스 표 + 날짜 선택) | ✅ |
| 4 | 변동 계산 → 변동 현황 화면 | ✅ |
| 5 | 예약 + 데일리 판매 현황 상단 알림 | ✅ |
| 6 | 채널 API 자동 수집 (채널별로 하나씩) | ⬜ |

API 연동을 마지막에 두는 이유는 채널마다 사정이 크게 달라서다.
전체 화면이 CSV 만으로 먼저 돌아가야 안전하다.

## 6단계 참고 — 채널별 API 사정

앞선 조사에서 확인한 내용이다. 10개 중 API 자동수집이 실제로 되는 건 절반이 안 된다.

| 채널 | 상태 | 메모 |
|---|---|---|
| 스스_MO / 스스_GY | 🟢 가능 | 네이버 커머스API센터. **호출 IP 사전 등록 필수** → Worker 고정 IP 문제 확인 필요 |
| 11번가 | 🟢 가능 | 셀러오피스 오픈API 키. 응답이 XML |
| 옥션 / 지마켓 | 🟡 신청 후 | ESM Trading API. ESM+ 마스터ID 생성 후 이용신청 |
| 토스_GY | 🟡 신청 후 | 토스쇼핑 셀러센터 '내 연동 키' |
| SSG | 🟠 승인 필요 | 파트너오피스 API 신청 |
| 카카오_MO / 카카오_GY | 🔴 어려움 | 톡스토어 상품목록 조회 API 는 있으나 전 판매자 대상이 아님(심사 선정) |
| 알리익스프레스 | 🔴 어려움 | Open Platform 앱 심사. 한국 셀러는 통상 솔루션사 경유 |

막힌 채널은 통합솔루션(사방넷·이지어드민·플레이오토 등) 경유나 셀러센터 CSV 다운로드로 채운다.
그래서 CSV 업로드는 임시방편이 아니라 **1급 입력 경로**다.

### 인증 방식 메모 (`../channel-sync/` 에서 확인한 것)

- **네이버 커머스API** — `client_secret` 을 salt 로 쓴 bcrypt 서명. `bcrypt.hashSync(clientId_timestamp, secret)` 를
  base64 로 감싸 토큰을 받는다. 순수 JS bcrypt 구현이 필요하다.
- **11번가** — 헤더 `openapikey` 에 키만 넣으면 되지만 응답이 XML 이다. 단건/목록에서 노드 모양이 달라지므로
  배열 정규화가 필요하다. 개발가이드가 셀러오피스 로그인 뒤에만 열려서 경로는 실물로 한 번 확인해야 한다.
- **쿠팡(이번 스펙에는 없음)** — `CEA` 서명. `signed-date + METHOD + path + query` 를 HMAC-SHA256.
- **카페24(이번 스펙에는 없음)** — refresh token 이 사용할 때마다 회전한다. 갱신값을 반드시 저장해야 다음 실행이 산다.
