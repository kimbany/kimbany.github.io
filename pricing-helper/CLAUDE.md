# 판매가 설정 도우미

## 이 프로젝트가 다루는 것

**판매 전에 가격과 코드를 정하는 도구.** 두 가지를 한다.

1. **판매가 역산** — 원가를 넣으면 "채널마다 얼마에 팔아야 하는지"를 계산한다.
2. **제품코드 생성** — 브랜드·분류·중량·입수량을 조합해 제품코드를 만들고 관리한다.

판매 채널마다 수수료가 다르고, 채널에 붙은 자사 브랜드마다 포장비가 다르고,
무료배송이면 택배비까지 판매자가 떠안는다. 이 셋을 채널별로 각각 대입해서
목표 마진율이 남는 판매가를 뽑아 준다.

### 제품코드

`MO-GP-SH-2000G-0203` 처럼 **브랜드 - 대분류 - 옵션분류 - 중량·수량 - 입수량**을
이어 붙인 코드를 만든다. 채널마다 제품을 등록할 때 쓰는 자체 식별자다.
코드를 조합할 재료(분류)를 먼저 등록해 두고, 그 재료만 골라서 코드를 만든다.

**이 프로젝트가 다루지 않는 것 — 매출 집계, 주문·재고, 정산.**
### 판매가 역산
매출 통합은 `../sales-report/`, 채널별 판매상태는 `../channel-status/` 가 담당한다.
여기는 "판매 전에 가격을 정하는" 단계만 본다.

## 디렉터리

```
pricing-helper/
  CLAUDE.md          이 문서 (설계 결정과 계산 규칙)
  INITIAL_PROMPT.md  최초 요청서 + 확정된 답변 원문
  README.md          사용자용 안내
  index.html         앱 전체 (단일 파일)
```

## 기술 스택

`../sales-report/` · `../channel-status/` 와 같은 구성으로 간다.

- **단일 HTML 파일** — 프레임워크·번들러 없음
- **Tailwind CSS CDN**
- **Firebase Firestore** — 채널 · 브랜드 · 택배 설정값 저장소.
  `index.html` 상단 `파이어베이스설정` 을 채우면 Firestore 모드,
  비워 두면 같은 인터페이스의 `localStorage` 어댑터(로컬 모드)로 동작한다.
  현재 화면 우상단 배지가 어느 모드인지 항상 표시한다.
- **GitHub Pages** 배포 — `https://invedory.com/pricing-helper/`

## 명명 규칙

- **함수명과 주석은 한글로 쓴다.** `판매가역산()`, `백원올림()` 처럼.
- **Firestore 컬렉션·문서 ID 는 ASCII 로 쓴다.** 문서 ID 에 한글이 섞이면 인코딩 사고가 나기 쉽다.
  객체 필드명은 한글을 쓴다(`채널명`, `포장비`).
- **용어는 "제품" 으로 통일한다. 화면·코드 어디에도 "상품" 이 들어가면 안 된다.**
  ("상품명" 이 아니라 "제품명", "상품코드" 가 아니라 "제품코드".)
  `../sales-report/` 는 "상품명" 을 쓰지만 이 프로젝트는 별개다. 옮겨 오지 말 것.
- **코드 값은 저장할 때 대문자로 통일한다**(`코드정규화()`).
  대소문자만 다른 코드가 둘 생기면 같은 제품이 다른 코드를 갖게 된다.

## 확정된 계산 규칙

이 6가지는 사용자가 직접 결정한 값이다. **임의로 바꾸지 않는다.**

### 1. 마진율은 판매가 대비다

```
판매가 = (원가 + 포장비 + 택배비) ÷ (1 − 수수료율 − 마진율)
```

마진율 30% = "판매가의 30% 가 마진으로 남는다". 수수료와 같은 기준이라
한 분모에 나란히 들어간다. `수수료율 + 마진율 >= 100%` 면 분모가 0 이하라
계산이 불가능하므로 값을 만들어 내지 말고 카드에 **계산 불가** 로 표시한다.

### 2. 택배비는 "자사 브랜드 › 택배" 에서 관리한다

- 자사 브랜드 대메뉴 아래 중메뉴 2개: **브랜드** / **택배**
- 택배 화면: 추가 · 수정 · 삭제, 항목마다 `택배명` + `택배비(원)`,
  라디오 버튼으로 **기본 택배비** 1개를 지정해 저장
- 판매가 계산 화면의 택배비는 **체크박스가 아니라 드롭다운**이다.
  등록된 택배 항목 중 하나를 골라 계산에 반영하고, "택배비 미포함(구매자 부담)" 도 고를 수 있다.
  화면을 열면 기본 택배비가 미리 선택되어 있다.
- 포장비는 브랜드에, 택배비는 택배 항목에 있다. 둘을 한곳에 합치지 않는다.

### 3. 원가는 판매 1건 기준, 입수량은 표시용

입력한 원가 = 실제로 팔 1건(1세트)의 원가다. 입수량(n개~n개)은 제품 정보로
결과 카드에 함께 적기만 하고 **나눗셈에 쓰지 않는다.**
단위 환산은 "원가 계산" 화면에서 이미 끝내고 넘어오므로, 여기서 또 나누면 이중 나눗셈이 된다.

### 4. 모든 금액은 VAT 포함이다

원가 · 포장비 · 택배비 · 결과 판매가 전부 VAT 포함 금액으로 통일한다.
별도 환산 로직을 두지 않는다.

**금액·퍼센트를 입력받는 모든 칸과 계산 결과를 보여주는 모든 곳에
"VAT 포함" 안내 문구를 붙인다.** (`VAT배지()` 헬퍼를 쓴다.)

### 5. 끝자리 — 100원 올림이 기본, 800원가는 보조 표기

- **대표 판매가 = 100원 단위 올림.** 12,340원 → 12,400원.
  항상 올림이라 목표 마진율을 밑돌지 않는다.
- **그 아래 작게 800원으로 끝나는 가격도 함께 보여준다.** 규칙은 "올림":
  13,450원 → 13,800원 (12,800원 아님), 14,110원 → 14,800원 (13,800원 아님).

  ```
  천단위 = floor(금액 / 1000) × 1000
  후보  = 천단위 + 800
  후보 < 금액 이면 후보 += 1000
  ```

- 두 가격 모두 **반올림 후 실제 마진율을 다시 계산해서** 함께 표시한다.
  올림한 판매가로 수수료를 다시 곱해야 실제로 남는 돈이 나온다.

## 확정된 제품코드 규칙

이 6가지도 사용자가 직접 결정한 값이다. **임의로 바꾸지 않는다.**

### 1. 브랜드는 한 곳에서만 관리한다

`「자사 브랜드 › 브랜드」` 와 `「제품코드 › 분류 › 브랜드 생성」` 은 **같은 목록**이다
(`저장소.캐시.브랜드` 하나). 어느 쪽에서 등록하든 브랜드 한 줄이 되고,
포장비는 자사 브랜드 화면에서만 넣는다. 두 화면의 저장은 `브랜드공통저장()` 하나로 처리한다.

브랜드 코드는 자사 브랜드 화면에서는 **선택**(제품코드가 생기기 전에 등록한 브랜드가 있어서),
분류 화면에서는 **필수**다. 코드가 없는 브랜드는 제품코드 생성 드롭다운에서 `disabled` 로 나온다.

### 2. 코드 순서와 자릿수

```
브랜드 - 대분류 - 옵션분류 - 중량·수량 - 입수량

구분형코드   MO-GP-SH-2000G-0203      ← 하이픈으로 끊는다
연속형코드   MOGPSH2000G0203          ← 같은 조각을 그냥 이어 붙인다
```

- **입수량은 두 자리씩 붙인다.** 2개~3개 → `0203`, 10개~12개 → `1012`.
  **0~99 만 허용**하고 100 이상은 등록할 때 막는다. 코드 길이가 항상 4자리여야 자리가 밀리지 않는다.
- **중량 단위는 G / EA 두 개뿐이다.** 2kg 은 `2000` + `G` 로 등록해 `2000G` 가 된다.
  KG 단위를 만들지 않는다. 같은 중량이 `2KG` 와 `2000G` 두 코드로 갈라지는 것을 막기 위해서다.
  입력칸 아래에 `2,000 G (2kg)` 처럼 환산을 보여 주는 것으로 대신한다.

### 3. 대분류와 옵션분류는 한 줄에 저장한다

`대분류/{id}` 한 줄이 `{ 대분류명, 대분류코드, 옵션분류명, 옵션분류코드 }` 를 함께 갖는다.
**같은 대분류코드를 쓰는 줄이 여러 개면 그 대분류에 옵션분류가 여러 개 달린 것이다.**

- 같은 대분류코드에 **다른 대분류명**이 오면 막는다. 코드 하나에 이름 하나여야 한다.
- 같은 `(대분류코드, 옵션분류코드)` 조합은 막는다.
- **대분류명·대분류코드는 대분류 전체의 속성이다.** 한 줄에서 고치면 같은 대분류코드를 쓰던
  다른 줄도 함께 따라간다. 옵션분류명·옵션분류코드만 그 줄에 한정된다.

**대분류 하나에 옵션분류가 여러 개인 것이 오히려 보통이다.** 그래서 생성 폼의 옵션분류는
`+` / `−` 로 줄을 늘렸다 줄이는 목록(`옵션분류칸들`)이고, 저장 한 번에 여러 줄이 함께 등록된다.
`감귤류 CT` 에 `만감 MG` · `노지감귤 NJ` · `한라봉 HL` 을 한 번에 넣는 식이다.

- **빈 줄은 건너뛴다.** 한쪽만 채운 줄은 실수이므로 몇 번째 줄인지 짚어서 막는다.
- **배치 안에서 옵션분류 코드가 겹치면** 저장 전에 막는다. 기존 항목과의 중복도 같이 본다.
- **수정 모드에서는 줄이 하나로 고정된다.** 고르고 있는 옵션분류 한 줄만 다루므로
  `+` 는 숨기고 `−` 는 비활성이다. (대분류명·코드를 고치면 위 규칙대로 그룹 전체가 따라간다.)
- 목록의 대분류 머리에 있는 **`+ 옵션분류`** 는 그 대분류의 이름·코드를 폼에 채워 준다.
  이미 있는 대분류에 옵션분류만 더 붙일 때 대분류를 다시 타이핑하지 않게 하기 위한 것이다.

### 4. 같은 제품은 두 번 만들지 않는다 — 입수량은 판정에서 뺀다

**`(브랜드ID, 분류ID, 중량ID)` 세 가지가 같으면 같은 제품으로 보고** 저장을 막으며
**기존 코드를 알려준다.** (`분류ID` 안에 대분류와 옵션분류가 함께 들어 있다.)

**입수량은 중복 판정에 넣지 않는다.** 같은 제품이라도 입수량은 그때그때 달라지는 값이라,
입수량이 다르다는 이유로 코드가 여러 개 생기면 한 제품에 식별자가 여러 개 붙는다.
제품코드는 채널·재고에서 식별자로 쓰이는 값이라 같은 제품에 코드는 하나여야 한다.
입수량이 바뀌면 새 코드를 만들지 말고 기존 코드를 **수정**한다.

### 5. 저장한 뒤 어디에 있을지는 어디서 왔느냐로 정한다

- **생성** — 화면을 그대로 둔다. 코드를 연달아 만드는 경우가 많다.
  드롭다운만 비우고 방금 만든 코드를 `#코드생성완료` 에 남겨 둔다.
- **수정** — 제품코드 목록으로 돌려보낸다. 목록의 「수정」에서 넘어온 흐름이기 때문이다.

### 6. 분류가 바뀌면 제품코드도 다시 계산한다

브랜드·대분류·중량·입수량의 코드를 고치면 그 재료로 만든 제품코드가 낡은 값이 된다.
분류 저장 직후 `제품코드전체재계산()` 이 참조가 살아 있는 건을 모두 다시 계산하고,
바뀐 건수를 토스트로 알린다. 참조가 지워진 건은 저장된 코드 문자열을 그대로 두고
목록에 `브랜드 삭제됨` · `분류 삭제됨` 처럼 표시한다.

### 7. 판매가 계산 연동은 만들되 숨겨 둔다

`제품코드연동표시` 상수가 `false` 인 동안 판매가 계산 화면의
`「제품코드 불러오기」`(`#제품코드불러오기영역`) 는 숨어 있다.
`true` 로 바꾸면 드롭다운이 나타나고, 고른 제품코드의 브랜드·분류·중량·입수량이
제품명 / 무게·수량 / 입수량 칸에 채워진다(`제품코드적용()`). 동작은 이미 다 들어가 있다.

## 데이터 구조

설정값은 몇 건 수준이라 **종류별 문서 1개에 배열로 담는다.** 읽기 3회로 전체 로드가 끝난다.

```
pricing_helper/channels
  목록  [ { id, 채널명, 수수료율, 브랜드ID, 정렬 } ]

pricing_helper/brands
  목록  [ { id, 브랜드명, 브랜드코드, 포장비 } ]      ← 판매가·제품코드가 함께 쓴다

pricing_helper/shipping
  목록  [ { id, 택배명, 택배비 } ]
  기본택배ID  "s..."          ← 라디오로 고른 기본 택배비 1개

pricing_helper/categories                            ← 제품코드를 조합할 재료
  대분류  [ { id, 대분류명, 대분류코드, 옵션분류명, 옵션분류코드 } ]
  중량    [ { id, 값, 단위 } ]        단위 = "G" | "EA"
  입수량  [ { id, 최소, 최대 } ]      0 ~ 99

pricing_helper/product_codes
  목록  [ { id, 브랜드ID, 분류ID, 중량ID, 입수량ID, 구분형코드, 연속형코드, 생성일 } ]
```

- **분류 세 종류는 문서 하나(`categories`)에 함께 담는다.** 각각 몇 건 수준이라
  문서를 나눌 이유가 없고, 화면 하나에서 셋을 같이 쓰므로 읽기 1회로 끝나는 편이 낫다.
- **`구분형코드`·`연속형코드` 를 계산해서 저장한다.** 매번 조합하지 않는 이유는
  재료가 지워져도 코드 문자열은 남아야 하기 때문이다. 대신 재료가 바뀌면
  `제품코드전체재계산()` 으로 다시 맞춘다.
- **`생성일` 은 밀리초 숫자**(`Date.now()`)로 저장하고 화면에서 `날짜표시()` 로 KST 로 바꾼다.

- `수수료율` 은 **0~1 실수가 아니라 퍼센트 숫자 그대로** 저장한다(10.5 = 10.5%).
  화면 입력값과 저장값이 같아야 사람이 Firestore 콘솔에서 봐도 헷갈리지 않는다.
  계산 직전 `퍼센트→비율()` 로 나눈다.
- `채널.브랜드ID` 가 가리키는 브랜드가 지워지면 포장비 0 으로 계산하고
  카드에 **브랜드 연결 끊김** 을 표시한다. 조용히 0 으로 넘기지 않는다.

## 화면 구성

```
판매가            (대메뉴)
  ├ 원가 계산     입고 단위 → 판매 단위 환산 원가. "판매가 계산으로 보내기" 로 값 전달
  └ 판매가 계산   원가 → 채널별 판매가 역산. 결과는 채널별 영수증 카드
제품코드          (대메뉴)
  ├ 제품코드 목록 검색 · 정렬 · 복사 · 수정 · 삭제
  ├ 제품코드 생성 드롭다운 5개로 조합. 미리보기 후 저장
  └ 분류          대분류 · 중량·수량 · 입수량 · 브랜드 CRUD (코드의 재료)
채널 기본설정      (대메뉴, 중메뉴 없음) 채널명 · 수수료% · 연결 브랜드 CRUD
자사 브랜드        (대메뉴)
  ├ 브랜드        브랜드명 · 브랜드코드 · 포장비 CRUD
  └ 택배          택배명 · 택배비 CRUD + 기본 택배비 라디오 선택
```

**만드는 순서는 분류 → 제품코드 생성 → 제품코드 목록이다.** 앞 화면에서 등록한 값을
뒷 화면이 가져다 쓴다. 메뉴에 보이는 순서(목록 → 생성 → 분류)와 반대인 것은 의도한 것이다.

### 결과 카드 규칙

- **채널 1개 = 카드 1개.** 영수증처럼 항목이 세로로 쌓인다.
- 마진율 입력칸이 여러 개면 **한 카드 안에서 마진율별로 구분**해 각각 보여준다.
  마진율마다 카드를 새로 만들지 않는다(채널 비교가 목적이므로 채널이 바깥 축이다).
- 각 마진율 블록에 **원가 · 포장비 · 택배비 · 수수료 · 마진 · 최종 판매가**를 모두 적는다.
  하나라도 0 원이면 생략하지 말고 `0원` 으로 적는다. 빠진 항목은 계산 착오로 읽힌다.
