# 매출 통합 대시보드 (v2)

여러 판매 채널(쿠팡 · 네이버 스마트스토어 · 11번가 · 카페24 등)에서 각각 내려받은 매출 엑셀을
업로드하면 **하나의 기준(브랜드 / 상품 / 규격)으로 통합 집계**하는 단일 HTML 웹 대시보드입니다.

👉 <https://invedory.com/sales-report/>

## 개발 단계

요청서(v2)의 9단계 계획을 **단계별로 확인하며** 진행합니다.

| Phase | 내용 | 상태 |
|---|---|---|
| 1 | HTML 뼈대 + 탭 4개 + 데이터 계층 + (Firebase 연결 준비) | ✅ |
| 2 | 셋팅: 채널 / 브랜드 / 상품·규격 CRUD | ✅ |
| 3 | 데이터 입력: 엑셀/CSV 파싱 + 미리보기 | ✅ 카페24(자사몰) |
| 4 | 매칭 엔진: matchKey 생성 + 4분류 | 🔸 자사몰 자동매칭만 |
| 5 | 중복 제거 + 저장 + 업로드 이력/롤백 | ✅ |
| 6 | 매칭 관리 트리 뷰 + 과거 데이터 재매칭 | ⬜ |
| 7 | 메인 화면 3단 집계 | ✅ |
| 8 | 매출 화면(기간·필터·CSV) | 🔸 차트 제외 |
| 9 | dailyStats 사전집계 최적화 | ⬜ |

**현재 = 자사몰(카페24 · 몽프루이) 매출 반영 완료.**
데이터 입력에서 카페24 주문내역(CSV/xlsx)을 올리면 메인·매출 화면에 바로 집계됩니다.
스마트스토어 · 11번가 · SSG · 쿠팡은 같은 틀로 이후 추가합니다.

## 자사몰(카페24) 업로드 — 지금 되는 것

1. **데이터 입력** 탭 → 카페24 주문내역 파일을 끌어다 놓기(또는 클릭) · 여러 파일 가능
2. **미리보기**에서 매출/순매출/수량/취소·중복 확인 후 **저장**
3. 저장하면 상품·규격·브랜드(몽프루이)가 **자동 등록**되고 메인/매출에 집계

### 카페24 파일 해석 규칙 (요청서대로)
- **행 단위 고유키 = 품목별 주문번호** (`20260907-0000062-01`) → 재업로드해도 중복 매출 방지
- **매출 = 총 상품구매금액**(판매가×수량), 주문번호가 같으면 **주문당 1회만** 합산(한 주문에 여러 품목이면 모든 행에 같은 총액이 찍히므로). 상품별 매출은 `옵션+판매가 × 수량` 으로 나눠 담고 합계는 총 상품구매금액과 일치
- **순매출 = 품목별 결제금액**(행별, 적립·쿠폰·추가할인 차감 후). 브랜드·상품별 표에 매출과 순매출을 나란히 표시
- **취소구분**이 `취소안함`이 아니면 매출에서 제외하고 취소 합계로 별도 집계
- 총 결제금액 · 소비자가격(정상가) · 추가할인 · 적립금 · 쿠폰 등은 함께 저장(향후 분석용)
- CSV 인코딩 UTF-8 / EUC-KR 자동 감지, .xlsx 도 지원

### 화면
- **메인**: 데이터가 있는 가장 최근 판매일 기준 매출·순매출·수량·취소 + 브랜드별 + 상품별(상품/규격 토글)
- **매출**: 기간 선택·퀵버튼(오늘/어제/최근7·30일/전체) + 채널·브랜드 필터 + 합계·일평균 + 브랜드/상품 분해 + CSV 내보내기
- **셋팅**: 채널·브랜드·상품·규격 CRUD (자사몰 채널은 자동 생성)

## 지금 할 수 있는 것 (Phase 2)

### 셋팅 › 채널 관리
- 채널 추가/수정/삭제: 채널명 · 채널코드 · 사용여부
- **엑셀 컬럼 매핑** 9종(주문번호 · 주문일 · 상품코드 · 상품명 · 옵션코드 · 옵션명 · 수량 · 판매금액 · 주문상태)
- **매출 기준일**(주문일 / 결제일 / 발송일)
- **상품코드 · 옵션코드 제공 여부** 토글 — 없으면 이름 기반 대체 매칭으로 동작하며 목록에 `⚠ 이름 기반 매칭` 표시
- **취소로 간주할 주문상태** 목록
- (헤더 시그니처 자동 지정은 Phase 3 업로드에서 파일을 올릴 때 채워집니다)

### 셋팅 › 브랜드 관리
- 브랜드 추가/수정/삭제, 채널별 취급 브랜드 지정

### 셋팅 › 상품 관리
- **브랜드 › 상품 › 규격** 2단계 구조
- 상품(그룹) 등록 후 그 아래 규격(1kg / 3kg / 12개입) 추가: 규격명 · SKU · 정가 · 단위타입(g/ml/ea) · 단위값
- 규격 = 매칭·집계의 최소 단위

### 셋팅 › 매칭 관리
- Phase 6에서 채널별 트리 뷰·과거 재매칭 구현. 현재는 구조와 빈 상태만 표시.

### 셋팅 › 기타
- JSON 백업 내보내기 / 가져오기, 전체 초기화, 저장 위치 안내

## 기술 / 데이터 계층

- **단일 HTML** + Tailwind CSS(CDN). 프레임워크·번들러 없음
- **데이터 계층은 Firestore 호환 인터페이스**(컬렉션 / 문서ID)로 설계했고,
  현재는 브라우저 `localStorage` 로 동작하는 **로컬 모드** 어댑터를 씁니다.
  `index.html` 상단의 `firebaseConfig`(주석) 를 채우면 같은 인터페이스로 Firestore 로 전환됩니다.
- 컬렉션: `channels · brands · products · productItems · channelMappings · uploads · sales · dailyStats`
  (구조는 요청서 §5 그대로. 이번 단계에서는 앞의 4개를 사용)

### 매칭 설계(요청서 §2)의 핵심 규칙 — 코드에 미리 반영

- 매칭 최소 단위는 **옵션**, 키는 `channelId + 상품코드 + 옵션코드` (옵션 없으면 `__NONE__`)
- **이름이 아니라 코드**로 매칭, 이름은 검증용 스냅샷
- 옵션명의 **숫자·단위 변화**(`3kg`→`5kg`)는 위험 변경으로 감지 — 정규식
  `/(\d+(?:\.\d+)?)\s*(kg|g|ml|l|개입|개|입|과|봉|팩|미)/i`
- 이 규칙들은 Phase 4 매칭 엔진에서 사용되며, 관련 유틸(`extractSpec` · `normalizeName`)을 미리 넣어 두었습니다.

## 저장 위치

로컬 모드에서는 데이터가 이 브라우저에만 저장됩니다(localStorage 키 `saleshub:v2`).
다른 기기와 공유하려면 셋팅 › 기타에서 JSON 백업을 내보낸 뒤 가져오거나, Firebase 설정을 연결하세요.
